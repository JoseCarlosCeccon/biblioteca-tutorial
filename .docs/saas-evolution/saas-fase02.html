Redis 8 no compose e o cliente do Bun

O Redis entra como mais um serviço do compose, com duas escolhas de propósito: sem porta publicada (só a rede interna o alcança, como o Postgres) e sem volume. Tudo o que ele vai guardar é derivado do Postgres, que continua sendo a fonte da verdade. Se o contêiner sumir, o servidor reconstrói.

O backend não precisa de pacote novo: o Bun traz um cliente Redis embutido (RedisClient).

O cliente Redis

Crie backend/src/infrastructure/redis.ts: o cliente, a função ready e o redisKey.

tsbackend/src/infrastructure/redis.ts
import { RedisClient } from "bun";

/**
 * Cliente Redis do próprio Bun. Sem fila offline: com o Redis fora do ar, cada
 * comando falha na hora, e quem chamou decide seguir sem o dado derivado, em vez
 * de a requisição ficar esperando a reconexão.
 */
export function createRedis(url: string, options: { autoReconnect?: boolean } = {}): RedisClient {
  return new RedisClient(url, { enableOfflineQueue: false, connectionTimeout: 2000, ...options });
}

/**
 * O Redis só guarda dados derivados do Postgres (cache e índice de busca). Sem
 * REDIS_URL a aplicação funciona do mesmo jeito, só que sem eles.
 */
export const redis: RedisClient | null = process.env.REDIS_URL ? createRedis(process.env.REDIS_URL) : null;

/**
 * A conexão é aberta no primeiro uso. Sem fila offline, um comando enviado antes
 * dela ficar pronta seria recusado; por isso quem usa o Redis passa por aqui.
 * Com o servidor fora do ar, connect() rejeita: recusa imediata ou, no máximo, o
 * connectionTimeout.
 */
export async function ready(client: RedisClient): Promise<RedisClient> {
  if (!client.connected) await client.connect();
  return client;
}

const PREFIX = process.env.REDIS_PREFIX ?? "biblioteca";

/**
 * Toda chave passa por aqui. O prefixo separa os ambientes que dividem o mesmo
 * Redis (a aplicação usa "biblioteca", os testes "biblioteca_test"), e o primeiro
 * trecho diz o módulo dono da chave, como acontece com as tabelas.
 */
export function redisKey(...parts: string[]): string {
  return [PREFIX, ...parts].join(":");
}

Três decisões aqui merecem atenção:

  • Sem fila offline (enableOfflineQueue: false): com o Redis fora do ar, um comando falha na hora em vez de esperar a reconexão. Quem chamou decide seguir sem o dado derivado.
  • ready(): a conexão do Bun abre no primeiro uso. Sem fila offline, um comando enviado antes de ela ficar pronta seria recusado, então todo uso passa por ready.
  • redisKey(): o primeiro trecho de toda chave diz o módulo dono dela (autoria, acervo), exatamente como cada tabela tem um módulo dono.

Cache-aside na busca de autores

A busca de autores (UC06) faz 1 + N consultas: uma para os autores e uma contagem de livros por autor. É um custo honesto para medir, e o cache vai evitá-lo na segunda vez. O padrão é o cache-aside: procura no Redis; se não estiver lá, busca no Postgres e guarda.

O difícil num cache nunca é guardar; é invalidar. Apagar a chave depois de cada escrita parece bastar, mas tem uma corrida:

#Leitura lentaEscrita
1não acha no cache e lê o Postgres (dado antigo)
2altera o Postgres, faz COMMIT e apaga a chave
3grava no cache o dado antigo que leu em 1

Depois do passo 3, o cache fica velho até expirar. A saída é uma geração. A leitura anota o número da geração antes de ir ao Postgres e grava o resultado nela. A escrita incrementa a geração. No passo 3, a leitura grava numa geração que ninguém mais lê.

Cada geração é um hash do Redis, com um campo por termo buscado. O Redis 8 trouxe o HSETEX, que dá TTL a cada campo: quando todos expiram, o hash some sozinho.

 * Lê a geração atual e, nela, o resultado do termo. Devolve null quando não há
 * Redis (bypass): quem chamou segue direto para o Postgres.
 */
export async function readCachedSearch(term: string, client: RedisClient | null = redis): Promise<{ generation: number; authors: AuthorView[] | null } | null> {
  if (!client) return null;
  try {
    await ready(client);
    const generation = Number(await client.get(GENERATION) ?? 0);
    const cached = await client.hget(generationHash(generation), field(term));
    return { generation, authors: cached === null ? null : JSON.parse(cached) as AuthorView[] };
  } catch (error) {
    console.warn("Cache de autores indisponível:", (error as Error).message);
    return null;
  }
}

/**
 * Grava na geração que estava valendo quando a leitura começou. Se uma escrita
 * invalidou o cache no meio do caminho, este resultado (talvez velho) vai para
 * uma geração que ninguém mais lê, e expira sozinho.
 */
export async function writeCachedSearch(term: string, generation: number, authors: AuthorView[], client: RedisClient | null = redis): Promise<void> {
  if (!client) return;
  try {
    await ready(client);
    await client.send("HSETEX", [generationHash(generation), "EX", String(TTL_SECONDS), "FIELDS", "1", field(term), JSON.stringify(authors)]);
  } catch (error) {
    console.warn("Cache de autores indisponível:", (error as Error).message);
  }
}

/**
 * Invalida todas as buscas de uma vez: a próxima leitura procura na geração
 * seguinte, que começa vazia. Chame depois do COMMIT; antes dele, uma leitura
 * concorrente ainda veria o dado antigo no Postgres e o gravaria na geração nova.
 */
export async function invalidateAuthorSearch(client: RedisClient | null = redis): Promise<void> {
  if (!client) return;
  try {
    await ready(client);
    await client.incr(GENERATION);
  } catch (error) {
    console.warn("Cache de autores indisponível:", (error as Error).message);
  }
}
Por que depois do COMMIT? Se a invalidação acontecesse dentro da transação, uma leitura concorrente ainda veria o dado antigo no Postgres (a transação não terminou) e o gravaria na geração nova, que é exatamente a que todos vão ler.

Embeddings e o índice vetorial dos livros

Um embedding é um vetor de números que representa o sentido de um texto: textos de sentido parecido viram vetores próximos. A busca semântica transforma cada livro num vetor (uma vez, ao indexar) e cada consulta em outro (a cada busca). Depois, pede ao Redis os livros cujos vetores estão mais perto do vetor da consulta.

Quem calcula o vetor é uma porta, como o Clock que você já conhece. A aplicação usa o Gemini. A suíte de testes usa um embedder de hash determinístico, que roda sem rede e sem chave.

A porta

Crie backend/src/shared/Embedder.ts: o contrato.

tsbackend/src/shared/Embedder.ts
/** O texto é guardado no índice (documento) ou é o que o usuário digitou (consulta). */
export type EmbeddingPurpose = "document" | "query";

/**
 * Port: transformar textos em vetores. O domínio não sabe se quem responde é o
 * Gemini, outro provedor ou o embedder de hash dos testes; só sabe que textos
 * de sentido parecido viram vetores próximos.
 */
export type Embedder = {
  /** Modelo + dimensão. Mudou o id, os vetores antigos não servem mais: o índice é recriado. */
  id: string;
  dimensions: number;
  /** Até que distância cosseno um resultado ainda conta como relacionado. Depende do modelo. */
  maxDistance: number;
  embed(texts: string[], purpose: EmbeddingPurpose): Promise<Float32Array[]>;
};

O id identifica modelo e dimensão: vetores de modelos diferentes não se comparam, então trocar o id recria o índice. O maxDistance é o limiar de relevância, e ele depende do modelo; você vai calibrá-lo no passo 08.

tsbackend/src/infrastructure/gemini.ts
import type { Embedder, EmbeddingPurpose } from "../shared/Embedder";

/** A API aceita no máximo 100 textos por chamada de batchEmbedContents. */
const BATCH_SIZE = 100;

const TASK_TYPES: Record<EmbeddingPurpose, string> = {
  document: "RETRIEVAL_DOCUMENT",
  query: "RETRIEVAL_QUERY",
};

/**
 * Adaptador do Gemini (plano gratuito, chave do Google AI Studio), chamado por
 * REST com fetch, sem SDK. Documentos e consultas usam taskTypes diferentes: o
 * modelo otimiza cada lado da busca. 768 dimensões bastam para títulos curtos e
 * ocupam um quarto do tamanho padrão (3072).
 */
export function createGeminiEmbedder(
  apiKey: string,
  { model = "gemini-embedding-001", dimensions = 768, maxDistance = 0.38, fetch = globalThis.fetch }:
    { model?: string; dimensions?: number; maxDistance?: number; fetch?: typeof globalThis.fetch } = {},
): Embedder {
  const url = `https://generativelanguage.googleapis.com/v1beta/models/${model}:batchEmbedContents`;

  async function embedBatch(texts: string[], purpose: EmbeddingPurpose): Promise<Float32Array[]> {
    const response = await fetch(url, {
      method: "POST",
      headers: { "Content-Type": "application/json", "x-goog-api-key": apiKey },
      body: JSON.stringify({
        // a referência marca taskType e outputDimensionality do topo como "deprecated" em favor
        // de embedContentConfig, mas no lote só o topo é respeitado (testado em 2026-10-29)
        requests: texts.map((text) => ({
          model: `models/${model}`,
          content: { parts: [{ text }] },
          taskType: TASK_TYPES[purpose],
          outputDimensionality: dimensions,
        })),
      }),
      signal: AbortSignal.timeout(10_000),
    });
    if (!response.ok) throw new Error(`Gemini respondeu ${response.status}`);
    const { embeddings } = await response.json() as { embeddings: { values: number[] }[] };
    // o Redis recusaria em silêncio um vetor do tamanho errado: melhor falhar alto aqui
    const wrong = embeddings.find((embedding) => embedding.values.length !== dimensions);
    if (wrong) throw new Error(`Gemini devolveu ${wrong.values.length} dimensões; o índice espera ${dimensions}`);
    return embeddings.map((embedding) => Float32Array.from(embedding.values));
  }

  return {
    id: `${model}-${dimensions}`,
    dimensions,
    maxDistance,
    async embed(texts, purpose) {
      const vectors: Float32Array[] = [];
      for (let start = 0; start < texts.length; start += BATCH_SIZE) {
        vectors.push(...await embedBatch(texts.slice(start, start + BATCH_SIZE), purpose));
      }
      return vectors;
    },
  };
}
A documentação nem sempre é a verdade. A referência da API marca taskType e outputDimensionality no topo de cada request como deprecated, em favor de um embedContentConfig. No lote, porém, a API ignora o embedContentConfig e devolve 3072 dimensões, que o índice de 768 recusa sem dar erro. Por isso o adaptador confere a dimensão e falha alto.

O embedder de hash

Crie backend/src/infrastructure/hashEmbedder.ts: cada palavra soma 1 numa posição do vetor.

tsbackend/src/infrastructure/hashEmbedder.ts
import type { Embedder } from "../shared/Embedder";

/** FNV-1a de 32 bits: um hash simples e estável para sortear a posição de cada palavra. */
function fnv1a(text: string): number {
  let hash = 0x811c9dc5;
  for (let i = 0; i < text.length; i++) {
    hash ^= text.charCodeAt(i);
    hash = Math.imul(hash, 0x01000193) >>> 0;
  }
  return hash;
}

/**
 * Embedder determinístico, sem rede, para os testes e para estudar o mecanismo.
 * Não entende significado, só sobreposição de palavras: cada palavra soma 1 numa
 * posição do vetor. "vingança" fica perto de "Vingança no mar", mas "mistério"
 * não fica perto de "Assassinato no Expresso do Oriente". Para isso existe o Gemini.
 */
export function createHashEmbedder(dimensions = 1024): Embedder {
  return {
    id: `hash-${dimensions}`,
    dimensions,
    maxDistance: 0.6,
    async embed(texts) {
      return texts.map((text) => {
        const vector = new Float32Array(dimensions);
        const words = text.toLowerCase().normalize("NFD").replace(/\p{M}/gu, "").split(/[^\p{L}\p{N}]+/u).filter(Boolean);
        for (const word of words) vector[fnv1a(word) % dimensions]! += 1;
        // a distância cosseno não existe para o vetor nulo
        if (words.length === 0) vector[0] = 1;
        return vector;
      });
    },
  };
}

  let dot = 0, na = 0, nb = 0;

O índice no Redis Query Engine

Cada livro vira um hash do Redis com o texto indexado ("título — autor") e o vetor em FLOAT32 binário. O FT.CREATE cria um índice HNSW com distância cosseno sobre esses hashes.

Crie backend/src/modules/catalog/infrastructure/bookIndex.ts: criar o índice, sincronizar alguns livros e reconciliar todos com o Postgres.

tsbackend/src/modules/catalog/infrastructure/bookIndex.ts
import type { RedisClient } from "bun";
import { embedder as defaultEmbedder } from "../../../infrastructure/embedder";
import { sql } from "../../../infrastructure/postgres";
import { ready, redis, redisKey } from "../../../infrastructure/redis";
import type { Embedder } from "../../../shared/Embedder";
import type { CatalogIntegration } from "../domain/CatalogIntegration";

/**
 * Índice vetorial dos livros no Redis Query Engine. Cada livro é um hash com o
 * texto indexado e o vetor (FLOAT32 binário); o índice HNSW acha os vizinhos
 * mais próximos de uma consulta. Tudo aqui é derivado do Postgres: pode ser
 * apagado e reconstruído a qualquer momento.
 */
const INDEX = redisKey("acervo", "livros");
const INDEX_MODEL = redisKey("acervo", "livros", "modelo");
const KEY_PREFIX = redisKey("acervo", "livro", "");

export type IndexResult = { indexed: number; removed: number };

export function bookIndexKey(id: number): string {
  return redisKey("acervo", "livro", String(id));
}

function isUnknownIndex(error: unknown): boolean {
  // Redis 8: "SEARCH_INDEX_NOT_FOUND Index not found"; versões anteriores: "Unknown index name"
  return /index not found|unknown index|no such index/i.test((error as Error).message);
}

/**
 * Garante que o índice existe para este embedder e diz se precisou criá-lo.
 * Vetores de outro modelo não se comparam com os deste: trocar de modelo apaga o
 * índice junto com os documentos (DD) e começa de novo.
 */
export async function ensureBookIndex(embedder: Embedder, client: RedisClient): Promise<boolean> {
  try {
    if (await client.get(INDEX_MODEL) === embedder.id) {
      await client.send("FT.INFO", [INDEX]);
      return false;
    }
    await client.send("FT.DROPINDEX", [INDEX, "DD"]);
  } catch (error) {
    if (!isUnknownIndex(error)) throw error;
  }
  try {
    await client.send("FT.CREATE", [
      INDEX, "ON", "HASH", "PREFIX", "1", KEY_PREFIX,
      "SCHEMA", "embedding", "VECTOR", "HNSW", "6",
      "TYPE", "FLOAT32", "DIM", String(embedder.dimensions), "DISTANCE_METRIC", "COSINE",
    ]);
  } catch (error) {
    // outra requisição criou o índice ao mesmo tempo
    if (/already exists/i.test((error as Error).message)) return false;
    throw error;
  }
  await client.set(INDEX_MODEL, embedder.id);
  return true;
}

/** O que o modelo lê de cada livro: o título e, para dar contexto, o autor. */
function indexText(title: string, authorName: string | undefined): string {
  return authorName ? `${title} — ${authorName}` : title;
}

async function syncIds(ids: number[], integration: CatalogIntegration, embedder: Embedder | null, client: RedisClient): Promise<IndexResult & { created: boolean }> {
  const result = { indexed: 0, removed: 0, created: false };
  const unique = [...new Set(ids)];
  if (unique.length === 0) return result;
  await ready(client);
  const rows = await sql`SELECT id, titulo AS title, autor_id AS "authorId" FROM livros WHERE id IN ${sql(unique)}` as { id: number; title: string; authorId: number }[];

  // remover não precisa de embedder: o livro saiu do Postgres, sai do índice
  const existing = new Set(rows.map((row) => row.id));
  for (const id of unique) {
    if (!existing.has(id)) result.removed += await client.del(bookIndexKey(id));
  }
  if (!embedder || rows.length === 0) return result;

  result.created = await ensureBookIndex(embedder, client);
  const pending: { id: number; text: string }[] = [];
  for (const row of rows) {
    const text = indexText(row.title, (await integration.author(sql, row.authorId))?.name);
    // só paga o embedding quando o texto mudou ou quando o vetor gravado não tem o
    // tamanho deste modelo: o índice recusa esse vetor em silêncio, e ele ficaria para sempre
    const key = bookIndexKey(row.id);
    const sameText = await client.hget(key, "texto") === text;
    const rightSize = await client.send("HSTRLEN", [key, "embedding"]) === embedder.dimensions * 4;
    if (!sameText || !rightSize) pending.push({ id: row.id, text });
  }
  if (pending.length === 0) return result;

  const vectors = await embedder.embed(pending.map((item) => item.text), "document");
  for (const [i, item] of pending.entries()) {
    const vector = vectors[i]!;
    const blob = Buffer.from(vector.buffer, vector.byteOffset, vector.byteLength);
    // send aceita Buffer em tempo de execução; os tipos do Bun só declaram string
    await client.send("HSET", [bookIndexKey(item.id), "texto", item.text, "embedding", blob as unknown as string]);
  }
  result.indexed = pending.length;
  return result;
}

/**
 * Atualiza o índice para estes livros, depois do COMMIT. Nunca lança: sem Redis
 * ou sem Gemini o livro fica fora do índice até a próxima reconciliação, e a
 * escrita no Postgres, que é o que importa, já aconteceu.
 */
export async function syncBookIndex(ids: number[], integration: CatalogIntegration, embedder: Embedder | null = defaultEmbedder, client: RedisClient | null = redis): Promise<IndexResult> {
  if (!client) return { indexed: 0, removed: 0 };
  try {
    const { created, ...result } = await syncIds(ids, integration, embedder, client);
    // índice novo (Redis reiniciado, modelo trocado): os outros livros também precisam entrar
    if (created) void reconcileBookIndex(integration, embedder, client);
    return result;
  } catch (error) {
    console.warn("Índice semântico indisponível:", (error as Error).message);
    return { indexed: 0, removed: 0 };
  }
}

/** Compara o índice inteiro com o Postgres: indexa o que falta e remove o que sobrou. */
export async function reconcileBookIndex(integration: CatalogIntegration, embedder: Embedder | null = defaultEmbedder, client: RedisClient | null = redis): Promise<IndexResult> {
  if (!client) return { indexed: 0, removed: 0 };
  try {
    await ready(client);
    const ids = new Set((await sql`SELECT id FROM livros` as { id: number }[]).map((row) => row.id));
    let cursor = "0";
    do {
      const [next, keys] = await client.scan(cursor, "MATCH", `${KEY_PREFIX}*`, "COUNT", 500);
      cursor = next;
      for (const key of keys) ids.add(Number(key.slice(KEY_PREFIX.length)));
    } while (cursor !== "0");
    const { created, ...result } = await syncIds([...ids], integration, embedder, client);
    return result;
  } catch (error) {
    console.warn("Índice semântico indisponível:", (error as Error).message);
    return { indexed: 0, removed: 0 };
  }
}

/** O nome do autor faz parte do texto indexado: renomeá-lo reindexa os livros dele. */
export async function syncAuthorBookIndex(authorId: number, integration: CatalogIntegration): Promise<void> {
  try {
    const rows = await sql`SELECT id FROM livros WHERE autor_id = ${authorId}` as { id: number }[];
    await syncBookIndex(rows.map((row) => row.id), integration);
  } catch (error) {
    console.warn("Índice semântico indisponível:", (error as Error).message);
  }
}

/**
 * Índice vetorial dos livros no Redis Query Engine. Cada livro é um hash com o
 * texto indexado e o vetor (FLOAT32 binário); o índice HNSW acha os vizinhos
 * mais próximos de uma consulta. Tudo aqui é derivado do Postgres: pode ser
 * apagado e reconstruído a qualquer momento.
 */
const INDEX = redisKey("acervo", "livros");
const INDEX_MODEL = redisKey("acervo", "livros", "modelo");
const KEY_PREFIX = redisKey("acervo", "livro", "");

export type IndexResult = { indexed: number; removed: number };

export function bookIndexKey(id: number): string {
  return redisKey("acervo", "livro", String(id));
}

function isUnknownIndex(error: unknown): boolean {
  // Redis 8: "SEARCH_INDEX_NOT_FOUND Index not found"; versões anteriores: "Unknown index name"
  return /index not found|unknown index|no such index/i.test((error as Error).message);
}

/**
 * Garante que o índice existe para este embedder e diz se precisou criá-lo.
 * Vetores de outro modelo não se comparam com os deste: trocar de modelo apaga o
 * índice junto com os documentos (DD) e começa de novo.
 */
export async function ensureBookIndex(embedder: Embedder, client: RedisClient): Promise<boolean> {
  try {
    if (await client.get(INDEX_MODEL) === embedder.id) {
      await client.send("FT.INFO", [INDEX]);
      return false;
    }
    await client.send("FT.DROPINDEX", [INDEX, "DD"]);
  } catch (error) {
    if (!isUnknownIndex(error)) throw error;
  }
  try {
    await client.send("FT.CREATE", [
      INDEX, "ON", "HASH", "PREFIX", "1", KEY_PREFIX,
      "SCHEMA", "embedding", "VECTOR", "HNSW", "6",
      "TYPE", "FLOAT32", "DIM", String(embedder.dimensions), "DISTANCE_METRIC", "COSINE",
    ]);
  } catch (error) {
    // outra requisição criou o índice ao mesmo tempo
    if (/already exists/i.test((error as Error).message)) return false;
    throw error;
  }
  await client.set(INDEX_MODEL, embedder.id);
  return true;
}

function indexText(title: string, authorName: string | undefined): string {
  return authorName ? `${title} — ${authorName}` : title;
}

async function syncIds(ids: number[], integration: CatalogIntegration, embedder: Embedder | null, client: RedisClient): Promise<IndexResult & { created: boolean }> {
  const result = { indexed: 0, removed: 0, created: false };
  const unique = [...new Set(ids)];
  if (unique.length === 0) return result;
  await ready(client);
  const rows = await sql`SELECT id, titulo AS title, autor_id AS "authorId" FROM livros WHERE id IN ${sql(unique)}` as { id: number; title: string; authorId: number }[];

  // remover não precisa de embedder: o livro saiu do Postgres, sai do índice
  const existing = new Set(rows.map((row) => row.id));
  for (const id of unique) {
    if (!existing.has(id)) result.removed += await client.del(bookIndexKey(id));
  }
  if (!embedder || rows.length === 0) return result;

  result.created = await ensureBookIndex(embedder, client);

  for (const row of rows) {
    const text = indexText(row.title, (await integration.author(sql, row.authorId))?.name);
    // só paga o embedding quando o texto mudou ou quando o vetor gravado não tem o
    // tamanho deste modelo: o índice recusa esse vetor em silêncio, e ele ficaria para sempre
    const key = bookIndexKey(row.id);
    const sameText = await client.hget(key, "texto") === text;
    const rightSize = await client.send("HSTRLEN", [key, "embedding"]) === embedder.dimensions * 4;
    if (!sameText || !rightSize) pending.push({ id: row.id, text });
  }
  if (pending.length === 0) return result;

  const vectors = await embedder.embed(pending.map((item) => item.text), "document");
  for (const [i, item] of pending.entries()) {
    const vector = vectors[i]!;
    const blob = Buffer.from(vector.buffer, vector.byteOffset, vector.byteLength);

    await client.send("HSET", [bookIndexKey(item.id), "texto", item.text, "embedding", blob as unknown as string]);
  }
  result.indexed = pending.length;
  return result;

/**
 * O Bun conversa em RESP3, e nele o FT.SEARCH responde um mapa
 * ({ results: [{ id, extra_attributes }] }). Em RESP2 a mesma resposta é uma
 * lista plana: [total, chave, [campo, valor], chave, [campo, valor], ...].
 */
export function parseKnnReply(reply: unknown, keyPrefix: string): KnnHit[] {
  const toHit = (key: string, distance: string) => ({ id: Number(key.slice(keyPrefix.length)), distance: Number(distance) });
  if (Array.isArray(reply)) {
    const hits: KnnHit[] = [];
    for (let i = 1; i < reply.length; i += 2) {
      const fields = reply[i + 1] as string[];
      hits.push(toHit(reply[i] as string, fields[fields.indexOf("distancia") + 1]!));
    }
    return hits;
  }
  const { results } = reply as { results: { id: string; extra_attributes: { distancia: string } }[] };
  return results.map((result) => toHit(result.id, result.extra_attributes.distancia));
}

  term: string,
  integration: CatalogIntegration,
  { embedder = defaultEmbedder, client = redis, limit = 10, now = new Date() }:
    { embedder?: Embedder | null; client?: RedisClient | null; limit?: number; now?: Date } = {},

Quando o Redis volta

Durante a queda, tudo degradou como planejado: a busca de autores respondeu BYPASS, o cadastro funcionou e a busca semântica deu 503. Mas as escritas daquele intervalo não conseguiram invalidar o cache nem indexar livros. Um livro cadastrado durante a queda ficaria fora da busca semântica até o servidor reiniciar.

A correção usa um gancho do cliente do Bun: onconnect roda na primeira conexão e em cada reconexão automática. É o momento exato de recalcular os dados derivados.

Solução de problemas

UNABLE_TO_VERIFY_LEAF_SIGNATURE no build ou unable to verify the first certificate no log. Algum antivírus (Norton, Kaspersky, Avast) ou rede corporativa está inspecionando o HTTPS. Os contêineres Linux não confiam no certificado que ele injeta. Desative a verificação de HTTPS do antivírus durante a aula ou use outra rede.

A busca semântica responde 503. Confira se infra/.env tem a chave e recrie a aplicação (docker compose -f infra/compose.yaml up -d --build app). O log do app mostra a causa.

Gemini respondeu 429. É o limite por minuto do plano gratuito: espere um pouco. Cada aluno deve usar a própria chave.

Fechamento

O Redis entrou sem mudar a fonte da verdade. Ele guarda duas coisas derivadas: um cache com invalidação correta (geração, depois do COMMIT, atravessando módulos pela integração) e um índice vetorial que se reconcilia com o Postgres sempre que pode ter ficado para trás. Se ele cair, a aplicação degrada e não quebra; se ele voltar, os dados se refazem sozinhos.
